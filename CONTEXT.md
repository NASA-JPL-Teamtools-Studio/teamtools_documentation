# Teamtools Studio

The Teamtools Studio (TTS) is a suite of interoperable Python libraries originating at NASA's Jet Propulsion Lab (JPL) in the Mission Operations section, providing shared infrastructure for flight mission data analysis, planning, and operations — and generalized for any complex system where failure is not an option.

## Language

**Teamtools Studio (TTS)**:
The umbrella name for the suite of ~25 interoperable repositories. All shared libraries are prefixed with `tts_`; mission adaptations follow the pattern `<mission>_<tool>`.
_Avoid_: "the framework," "the platform," "TTS suite"

**Mission adaptation**:
A set of repos (e.g., `demosat_data_utils`, `demosat_dexter`) that extend TTS core libraries for a specific mission or project. Adaptations depend on TTS core; they do not modify it.
_Avoid_: "plugin," "instance," "deployment"

**DemoSat**:
A fictional satellite that is an amalgamation of real Earth orbiters, used as the canonical sandbox and demonstration environment for the full TTS suite. DemoSat repos (`demosat_*`) simulate an end-to-end operations cycle including uplink planning and downlinked actuals.
_Avoid_: "demo," "example mission," "test satellite"

**Invulnerable pipeline**:
A processing pipeline in which individual data sources are isolated so that a failure in one (malformed input, missing file, parse error) does not halt processing of the others. Implemented via the `@invulnerable` decorator and `InvulnerableDataManager` in `tts_data_utils`.
_Avoid_: "fault-tolerant pipeline," "safe pipeline," "error-handling pipeline"

**Query library**:
A per-mission or per-data-source library (e.g., `oco2_query`, `fss_query`) whose sole responsibility is reading raw data from files or databases and returning typed `TtsDataFrame` subclasses. No analysis logic lives here.
_Avoid_: "data loader," "reader," "ingester"

**Data utils**:
The per-mission library of `TtsDataFrame` subclasses for that mission's data types (e.g., `oco2_data_utils`). Contains schema definitions, domain methods, and display logic. Does not do I/O.
_Avoid_: "data layer," "models"

**Ground system**:
The command-and-control software suite used to operate a spacecraft (e.g., AMPCS, MGSS, FPrime, YAMCS). Ground-system-specific data types (like EHA and EVR formats) are grouped by ground system within `tts_data_utils/multimission/`.
_Avoid_: "ground software," "GSW" (too broad)

**EHA (Engineering Health and Alarms)**:
Telemetry channel data — spacecraft sensor readings processed through limit checking to produce engineering units and alarm states. AMPCS-specific format implemented as `AmpcsEhaFrame`.
_Avoid_: "telemetry," "channel data," "EHA data" (redundant)

**EVR (Event/EVent Record)**:
Discrete event messages generated by onboard software at severity levels (diagnostic, warning, fatal, etc.). AMPCS-specific format implemented as `AmpcsEvrFrame`.
_Avoid_: "events," "log messages," "alarm messages"

**PowerTable**:
The HTML/Jupyter table rendering component from `tts_html_utils`. Produces styled, color-coded, expandable tables for engineering data display. The primary output format for operations reports and Jupyter notebooks.
_Avoid_: "HTML table," "formatted table," "display table"

**Dexter**:
The TTS disposition and review workflow library (`tts_dexter`). Operators use Dexter to stamp individual data rows (via `TtsRowSeries`) as reviewed, acknowledged, or requiring action.
_Avoid_: "review tool," "disposition tool"

**Dante**:
The TTS channel derivation library (`tts_dante`). Applies calibration formulas and mathematical transformations to time-series `TtsDataFrame` columns to produce derived channels. Depends on the expression engine in `tts_data_utils`.
_Avoid_: "derivation engine," "calibration tool"

## Coding Standards

These rules apply across all TTS repositories. They exist to maximize readability, extensibility, and compatibility. See `docs/philosophy.md` for the design principles behind them.

### Import style

Always use fully-qualified import paths. **Do not use relative imports** (`from .module import X`). The directory path must be visible in the import statement so readers can immediately locate the source.

```python
# Correct
from tts_data_utils.core.data_frame import TtsDataFrame
from tts_data_utils.invulnerable_data_manager.invulnerable_data_manager import InvulnerableDataManager

# Wrong — relative imports are forbidden
from .data_frame import TtsDataFrame
```

### Prefer class-based designs

Favor classes that can be subclassed by customer projects over standalone functions. TTS provides bricks, not tools. A class with `classmethod` hooks and overridable methods is almost always better than a function with many parameters, because customer projects can extend it without modifying TTS source.

### Docstrings and type hints

All public classes, methods, and functions must have docstrings. Use type hints for all parameters and return values. This keeps the codebase navigable for humans and AI agents alike.

```python
def filter_expr(self, expr: str) -> 'TtsDataFrame':
    """Filter rows where the given boolean expression is True."""
    ...
```

### Human-inspectable test artifacts

Automated assertions are necessary but not sufficient. When a feature produces visual output — HTML tables, CSV exports, rendered reports — tests must also write a human-inspectable artifact to a well-known location in the repo so a developer can open it and verify the result looks right with their own eyes.

**Rules:**
- Write artifacts to `src/<package>/test/core/test_files/<feature_name>_inspection.html` (or `.csv`) so they live next to other test fixtures.
- Use the **full `HtmlCompiler` pipeline** (not bare `.render()`) for HTML artifacts so that JavaScript, CSS, sorting, and filtering are included and functional.
- The test that writes the artifact must still pass with a programmatic assertion (e.g., the file was created and is non-empty). Human inspection is in addition to, not instead of, automated tests.
- Add a `print()` statement in the test that outputs the absolute path to the artifact so it is easy to find in the test runner output.
- Gitignore patterns must not exclude these files — they are part of the repo.

**Example: PowerTable with sorting and filtering**
```python
def test_write_inspection_html(self, styled_frame, tmp_path):
    from tts_html_utils.core.compiler import HtmlCompiler
    compiler = HtmlCompiler("Inspection: StyledFrame PowerTable")
    compiler.add_body_component(
        styled_frame.power_table(add_sorting="local", add_filters="local")
    )
    out = Path("src/tts_data_utils/test/core/test_files/power_table_inspection.html")
    compiler.render_to_file(out)
    print(f"\nHuman-inspectable output: {out.resolve()}")
    assert out.exists() and out.stat().st_size > 0
```

### Python version support

Write code that runs on **Python 3.6.8 and above**. This supports older mission deployments where Python versions cannot be easily upgraded.

When you use a language feature that requires a newer Python version, add a comment noting the minimum version and what functionality would improve if the version floor is raised:

```python
# Python 3.10+ would allow: match alarm_state:
# For now, use if/elif chains.
```

This policy is intentional — see `docs/philosophy.md` ("Projects manage their own risk," "Support the little guys, too"). A roadmap item exists to eventually raise the minimum version floor.
