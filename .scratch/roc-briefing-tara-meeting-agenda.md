# Meeting Prep: Tara Estlin — ROC Briefing

**Where things stand:** You told her you'd have a draft today. What exists instead is a deep
working spec (`.scratch/roc-briefing-spec.md`) — deliberately broader and deeper than any real
presentation, built so it can be mined down to size later. No need to frame that as a problem;
it just means this conversation is about direction, not review.

**Format:** Not a Q&A you run on her. A shared list of things neither of you has fully settled.
Bring the list, let her reorder or skip freely, and expect her answers to some of these to be
better than yours.

---

## Questions to work through together

### Framing

1. **Is "service-center fit" the right way in**, or is there a sharper way to get ROC to the same
   conclusion — that a shared core plus thin, customer-owned adaptation is already a
   service-center shape — without stating it outright?
2. **Should the pitch name the gap in scoped GDS explicitly**, or is there a way to make that
   point that reads as less like criticizing tooling the room already committed to?
3. **How much should the pitch lean on "operators doing devops"** as the thesis, versus leading
   with something more concrete like the adoption evidence?

### Register

4. **How does this room actually want to be talked to?** Does naming multimission-tooling
   failure modes up front read as candor, or as defensive throat-clearing before anyone's raised
   it?
5. **Where's the line on honesty about where TTS is still thin** — sustainment, community depth,
   effectively one person's bus factor — without it reading as an admission that undercuts the
   pitch?
6. **Does the Clipper situation need to be handled differently than "never named, addressed
   verbally only if raised"?** Is there anything about who's likely in the room, or the lab's
   memory of it, that changes that plan?

### The ask

7. **How far should the ask reach in a first meeting?** The current plan is a three-rung ladder —
   catalogue listing, adaptation-as-a-service, staffed Systems Teamtools Leads on customer
   missions. Does naming the top rung give the room something concrete to react to, or does it
   need to be earned first?
8. **What does a credible staffing model for that top rung actually look like** from someone who
   knows how ROC sources engineers today — is "pooled at ROC, embedded part-time, capability
   transfer not dependency" realistic, or naive?

### Evidence

9. **Is OCO-2 the right case study**, or does depth-over-breadth (smallest team, longest tenure)
   need a different mission to make the point convincingly?
10. **Does the adoption matrix need to be more accurate before it's shown to anyone outside TTS**,
    or is a candor footnote about its current state sufficient for this audience?

### Scope and sequencing

11. **What does the version of this pitch that gets politely filed away look like?** Naming that
    failure mode explicitly might be the fastest way to avoid landing there.
12. **What's the right next step after this conversation** — a full draft for her to review, a
    second working session, or straight to scheduling with ROC?
13. **Is there anyone else — on the ROC side, or ours — who should help shape this before it goes
    further?**
